# Discovery and content

Use this guide when starting a site, importing materials, or reorganizing existing content.

## Minimum discovery

Infer what is already known before asking. The minimum useful brief contains:

- purpose: job search, professional identity, portfolio, writing, community, or another stated goal;
- audience: recruiters, clients, peers, readers, or a mixed audience;
- identity: display name and a short accurate headline;
- routes: Home, About, Blog, and GitHub by default;
- languages: primary locale and whether Chinese/English are both needed;
- content sources: provided documents, Markdown, images, links, and existing code;
- visual direction: adjectives, references, brand colors, or an accepted default;
- delivery: local project only or a requested deployment target.

Do not force a questionnaire when these facts can be extracted from context. Ask a concise question only when the missing answer would produce materially different work.

## Content-source rules

Treat user-provided materials as the source of truth. Separate:

1. confirmed facts;
2. user preferences;
3. draft copy proposed by the agent;
4. placeholders requiring user input;
5. private or ambiguous information that should not be published.

Never silently turn a draft or inference into a fact. Flag contradictory dates, names, roles, URLs, or translations.

Do not expose addresses, phone numbers, private email addresses, employer details, document metadata, or other sensitive fields merely because they appear in a supplied file. Include them only when the user requests or clearly expects publication.

## Page-content guidance

### Home

Prioritize identity, value, and the next action. Include visible routes to About, Blog, and GitHub. Add projects, recent posts, skills, or availability only when there is real content.

Do not leave a large empty projects section when no projects are supplied.

### About

Choose a narrative, profile, or resume-like structure based on the user's goal. Potential sections include biography, current focus, experience, education, capabilities, selected work, interests, and contact details. Do not require every section.

### Blog

Accept Markdown as the default content format. Preserve the author's meaning and voice. Require or derive reviewable metadata: title, summary, publication date, locale, tags, draft status, and optional cover information.

If no posts exist, use a useful empty state. A demonstration article must be clearly labeled as sample content and removed or replaced before a production handoff unless the user wants it.

### Projects

For each project, prefer a title, accurate summary, technologies, repository URL, live URL, image, and featured flag. Omit unavailable fields. Do not infer technical choices from screenshots alone.

## Bilingual content

- Keep Chinese and English as distinct authored content, joined by a stable translation key.
- A translation generated by the agent is a draft until confirmed.
- Do not publish empty translated pages merely to make route counts match.
- Preserve names, product names, code identifiers, and URLs unless the user specifies localized forms.
- When one translation is missing, record it in the handoff rather than hiding the gap.

## Content brief template

Use this structure internally or show a concise version to the user:

```yaml
purpose: string
audience: string[]
primaryLocale: zh-CN | en
additionalLocales: string[]
pages: string[]
primaryAction: string
contentSources: string[]
confirmedFacts: string[]
draftCopy: string[]
missingContent: string[]
sensitiveFieldsExcluded: string[]
visualDirection: string
implementationPath: existing | user-selected | default
deployment: local | github-pages | vercel | netlify | other
```
